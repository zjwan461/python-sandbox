## 1. 项目概述

### 1.1 背景

`python-sandbox` 已具备面向 SDK 调用方的"沙箱化 Python/Shell/pip 执行 + 文件读写 + 容器会话"能力。目前存在如下缺口：

1. 没有任何对外的运营管理界面，运维与业务方只能直接登录数据库或读日志文件。
2. 没有"客户端（应用）"概念，调用方是被隐式的、无身份可追溯、无 ApiKey、无配额。
3. 没有限流能力，存在被单个调用方拖垮整个 Docker Daemon 与宿主资源的风险。
4. 没有运行中会话的可见性面板，运维只能凭日志推断。
5. 没有自审计（登录、操作日志）能力，出现纠纷难以回溯。

### 1.2 目标

为 `python-sandbox` 增加一套前后端分离的"管理端"，并对原 `python-sandbox` 后端做必要的接入改造，以实现：

* 对外提供标准 RBAC 管理界面，覆盖"管理员 / 普通用户"两类核心角色的日常工作。
* 把现有 SDK 调用方抽象为"客户端 + ApiKey"，可被管理、可被限流、可被审计。
* 提供运行中容器的可见性，并允许管理员强制销毁。
* 把现有"裸 SQL 直接查日志"的工作流升级为"页面 + 筛选 + 链路追踪"。
* 沉淀管理端自身的登录与操作审计，符合最小必要的可追溯要求。

### 1.3 范围

#### 1.3.1 包含（In-Scope）

* 管理端前端应用。
* 管理端后端应用。
* 在现有 MySQL 库内新增"管理端相关"业务表，与原 `api_log`、`sandbox_operation_log` 共库存在。
* 对现有 `python-sandbox` 后端做必要的接口/拦截改动，以提供：ApiKey 校验、限流、运行中会话强制销毁、日志字段补全。
* 管理端自身的操作审计与登录审计。

#### 1.3.2 不包含（Out-of-Scope）

* 调用方用户体系的二次身份认证（如 OAuth、CAS、SSO、短信登录）。
* 沙箱执行环境本身的优化（只对接，不重写）。
* 数据大屏、BI、报表导出到 Excel 等高级分析能力。
* 任何对 SDK 接口协议的破坏性变更（保留向后兼容）。
* 多租户隔离（仅单租户视角；不同客户端/用户在管理端内做逻辑隔离）。
* 终端用户计费、对账、发票等业务。

### 1.4 模块边界

| 模块 | 角色 | 关键职责 |
|------|------|----------|
| 管理端前端 | 面向"管理员/普通用户"的浏览器 UI | 登录、CRUD、查询、可视化 |
| 管理端后端 | 管理端的业务服务与权限中枢 | RBAC 校验、对外接口、聚合查询、与 python-sandbox 互通 |
| python-sandbox 后端（已存在） | 实际承载 Sandbox 执行能力 | 提供"ApiKey 校验入口"、"限流能力"、"运行中会话查询/销毁"、"日志查询"等对接点 |
| 数据库（共用） | 持久层 | 新增管理端业务表；保留既有 `api_log`、`sandbox_operation_log` |

### 1.5 名词定义

| 名词 | 定义 |
|------|------|
| 客户端（Client） | 一个被抽象出来的"调用方应用"，代表某一类接入者（产品/团队）。 |
| ApiKey | 客户端持有的调用凭证；在 python-sandbox 后端被用于鉴权。 |
| 限流规则 | 针对 ApiKey / 客户端的频次阈值，由管理端配置并下发。 |
| Sandbox 会话 | 与 `python-sandbox` 后端内的容器一一对应；含 `sessionId`、`containerId`、`创建时间`、`最后活跃时间`。 |
| RBAC | 基于"用户—角色—菜单/权限"模型的访问控制。 |
| 链路追踪 | 通过 `traceId` 把"一次请求 → 多个沙箱操作 → 日志行"串起来的能力。 |
| traceId | 已存在，由 `python-sandbox` 的 `TraceFilter` 生成，通过 ThreadLocal + 响应头 `X-Trace-Id` 暴露。 |

## 2. 现状梳理（用于对齐对接口径）

> 本节是从原项目"读出来的事实"，不是要新增的"需求"。后续 Design agent 可基于此节进行对接设计。

### 2.1 已存在实体（管理端只读或需补字段，不可破坏）

* 表 `api_log`：字段 `id, trace_id, session_id, api_path, http_method, request_params, response_code, execution_time, client_ip, created_at`。无 `client_id / api_key_id / user_id`。
* 表 `sandbox_operation_log`：字段 `id, trace_id, session_id, operation_type, operation_content, result, exit_code, stdout, stderr, execution_time, error_message, created_at`。枚举值覆盖 `PYTHON_EXEC / SHELL_EXEC / PIP_INSTALL / PIP_UNINSTALL / PIP_LIST`。

### 2.2 已存在机制

* 数据库名 `sandbox`，字符集 `utf8mb4`。管理端业务表必须建在同一库中。
* `python-sandbox` 的 API 入口前缀为 `/api/sandbox/*`，已通过 `ApiLogAspect` 自动落库 `api_log`。
* 通过 `SandboxOperationLogAspect` 自动落库 `sandbox_operation_log`，枚举见上。
* `traceId` 由 `TraceFilter` 在入口生成，可由 `X-Trace-Id` 头透传；在 `api_log` 与 `sandbox_operation_log` 中均存在。
* 容器命名规则：`{containerNamePrefix}{sessionId}`（具体前缀来自现有配置），通过该规则可以反查容器与会话。
* 会话的生命周期：进程内 `ConcurrentHashMap<String, SandboxSession>` 维护，**当前不落库**；过期间隔由定时任务驱动清理。
* 强制销毁会话有对外接口：`DELETE /api/sandbox/session/{sessionId}`，但目前没有"列出全部活跃会话"的对外接口。
* 没有 ApiKey、限流、用户/角色/菜单、客户端等概念。

### 2.3 与 `python-sandbox` 后端必须新增的对接点（结论性需求，详见 §7）

下列能力在原系统中"不存在"，属于本管理端项目必须推动新建的最小改造集合。具体设计由 Design agent 在既有约束内落地。

1. ApiKey 校验入口：对所有 `/api/sandbox/*` 请求生效，向下兼容旧调用（缺失时给出"未授权且不允许匿名"的明确语义）。
2. 限流判定入口：可作用于 ApiKey 维度或客户端维度。
3. 活跃会话的列表/详情查询接口。
4. `api_log`、`sandbox_operation_log` 增加"客户端 / ApiKey / 归属用户"等字段以支撑管理端筛选（不破坏既有列语义）。
5. 管理端与 `python-sandbox` 之间的内部调用鉴权（管理端 → python-sandbox 的接口调用）。

## 3. 用户与角色

### 3.1 角色矩阵

| 角色 | 描述 | 关键权限范围 |
|------|------|---------------|
| 超级管理员 | 系统初始化时内置的唯一账号 | 全部菜单、全部数据、所有租户可见性无关的全局操作 |
| 管理员 | 运营/运维人员 | 用户/角色/菜单/客户端/ApiKey/限流/运行中会话/调用记录/审计日志的全面管理 |
| 审计员（建议） | 只读安全与合规岗位 | 仅可查看日志、运行中会话（只读）、客户端状态；无修改权限 |
| 普通用户 | 业务方使用人 | 只能创建并管理"自己名下的"客户端与 ApiKey；只能查看自己产生的调用记录 |
| 匿名调用方 | 持有 ApiKey 但未登录管理端的 SDK | 无法登录管理端；只能走 `/api/sandbox/*` |

> 角色命名仅作模型示意，是否落地"审计员"请由用户在架构阶段确认。

### 3.2 权限模型

* 采用经典"用户—角色—菜单/权限"模型。
* 菜单用于"路由与页面可见性"，按钮权限（如 `apikey:edit`、`apikey:revoke`）用于"控件可见性"。
* 角色与菜单/权限为多对多。
* 用户与角色为多对多；一个用户至少挂一个角色。

## 4. 功能需求

每个需求有唯一 `FR-xxxx` 编号，括号内为建议优先级（`P0` 必须 / `P1` 重要 / `P2` 可选）。

### 4.1 登录与认证（FR-AUTH）

* **FR-AUTH-01 账号密码登录（P0）**：支持使用"用户名 + 密码"登录管理端。同一账号连续登录失败超过阈值后锁定一段时间（阈值与时长由管理端配置项决定，写入"假设与依赖"）。
* **FR-AUTH-02 图形验证码（P0）**：登录页需展示图形验证码，验证码错误时不消耗登录失败次数；登录失败到阈值前几次可要求验证码。
* **FR-AUTH-03 "记住我"自动登录（P1）**：勾选后下次访问自动续登；超过最长免登天数或用户主动登出后失效。
* **FR-AUTH-04 退出登录（P0）**：清除本地会话与管理端服务端会话。
* **FR-AUTH-05 锁定与解锁（P1）**：管理员可在"用户管理"中手动解锁被锁定的账号。
* **FR-AUTH-06 自身密码修改（P0）**：登录用户可在个人中心修改自己的密码；修改后未失效的旧令牌立即作废。
* **FR-AUTH-07 首次登录强制修改初始密码（P1）**：超级管理员重置/创建用户后，该用户首次登录被强制跳转到修改密码页。

### 4.2 用户管理（FR-USER）

* **FR-USER-01 用户列表（P0）**：支持按用户名/昵称/手机/邮箱/状态/角色/部门筛选；支持分页、按字段排序。
* **FR-USER-02 新增/编辑用户（P0）**：字段包含用户名、昵称、姓名、邮箱、手机、性别、所属部门、角色集合、状态。
* **FR-USER-03 删除用户（P0）**：支持单删与批量删除；已被登录或仍持有"未撤销 ApiKey"的用户的删除策略详见 §4.7。
* **FR-USER-04 启停用用户（P0）**：停用账号后该用户无法登录、其 ApiKey 在 `python-sandbox` 端被拒绝调用。
* **FR-USER-05 重置密码（P0）**：管理员可对任意账号发起重置，生成新密码或下发一次性重置链接。
* **FR-USER-06 分配角色（P0）**：在新增/编辑页为用户绑定一个或多个角色。
* **FR-USER-07 导入与导出（P2）**：支持 CSV 批量导入/导出用户基础信息。
* **FR-USER-08 个人中心（P0）**：查看与修改自己的昵称/邮箱/手机/头像；任何修改影响登录用户自身的展示。

### 4.3 角色管理（FR-ROLE）

* **FR-ROLE-01 角色列表（P0）**：按名称/编码/状态筛选。
* **FR-ROLE-02 新增/编辑/删除角色（P0）**：字段包含名称、权限字符（如 `common`）、排序号、状态、备注。
* **FR-ROLE-03 分配菜单/权限（P0）**：为角色分配菜单与按钮权限（树形勾选 + 按钮平铺）。
* **FR-ROLE-04 内置角色保护（P1）**：系统内置角色（如超级管理员）的删除/降级需走"二次确认 + 校验不被业务引用"。

### 4.4 菜单与权限管理（FR-MENU）

* **FR-MENU-01 菜单树（P0）**：以树形结构维护菜单，含类型（目录/菜单/按钮）、父级、排序、图标、路由、组件、是否外链、是否缓存、是否可见等。
* **FR-MENU-02 按钮权限标识（P0）**：以"权限字符"形式管理按钮级权限，命名格式由管理端统一约束，详见 §10。
* **FR-MENU-03 排序与显隐（P1）**：支持拖拽排序、目录与菜单的可见性切换。
* **FR-MENU-04 路由生成依据（P1）**：管理端前端根据用户菜单权限自动生成可访问路由。

### 4.5 部门/组织（FR-DEPT，可选）

* **FR-DEPT-01 部门树（P2）**：增删改查，字段含名称、父部门、排序、负责人、状态。
* **FR-DEPT-02 与用户关联（P2）**：用户在"部门"维度上可挂多个岗位；列表可按部门筛选。
* **FR-DEPT-03 单点维护（P2）**：删除部门时若仍有用户，要求用户先迁移或同步停用。

> 若不引入"部门"，则把"FR-USER-02 中的所属部门"项退化为可空文本字段。不影响后续模块。

### 4.6 客户端（Client）管理（FR-CLIENT）

* **FR-CLIENT-01 客户端列表（P0）**：按"客户端名称 / 客户端编码 / 归属人 / 状态"筛选。
* **FR-CLIENT-02 新增/编辑客户端（P0）**：字段包含客户端名称、客户端编码（唯一）、描述、归属用户、状态、备注。
* **FR-CLIENT-03 启停用客户端（P0）**：停用后其名下所有未过期的 ApiKey 立即在 `python-sandbox` 端被拒绝。
* **FR-CLIENT-04 删除客户端（P0）**：删除前需提示"是否一并处理名下 ApiKey"；不允许直接删除仍持有有效 ApiKey 的客户端。
* **FR-CLIENT-05 客户端统计卡片（P1）**：列表页展示"该客户端下的 ApiKey 数 / 活跃 ApiKey 数 / 今日调用次数 / 累计调用次数"。
* **FR-CLIENT-06 客户端归属转移（P1）**：可将客户端从 A 用户转移到 B 用户，转移后调用记录的归属一并更新。

### 4.7 ApiKey 管理（FR-APIKEY）

* **FR-APIKEY-01 生成 ApiKey（P0）**：在客户端下创建；字段包含：名称、绑定客户端、绑定用户（可空，意味着以客户端维度计）、过期时间（可空，永不过期）、备注。
* **FR-APIKEY-02 明文一次性展示（P0）**：ApiKey 在生成后**仅展示一次明文**，之后任何界面/接口只能展示前缀（用于识别）+ 后 4 位掩码；明文不可恢复。
* **FR-APIKEY-03 状态管理（P0）**：状态机为 `启用 / 停用 / 已过期 / 已撤销`；前端列表有明显的状态标签与筛选。
* **FR-APIKEY-04 撤销（P0）**：管理员或归属用户可立即撤销；撤销不可逆。
* **FR-APIKEY-05 过期与生效（P0）**：未到生效时间或超过过期时间的 ApiKey 一律被 `python-sandbox` 拒绝调用，日志中体现原因。
* **FR-APIKEY-06 复制与新生成（P1）**：前端提供"复制明文"按钮（仅一次性展示期内）；提供"重新生成"动作重新走一次明文展示。
* **FR-APIKEY-07 列表筛选（P0）**：按客户端、用户、状态、过期时间范围筛选。
* **FR-APIKEY-08 操作审计（P0）**：所有 ApiKey 的"创建/启停/撤销/重新生成"均落入管理端审计日志。

### 4.8 限流规则（FR-RATELIMIT）

* **FR-RATELIMIT-01 规则模型（P0）**：规则维度可选择 `ApiKey / 客户端`；窗口可选择 `分钟 / 小时 / 天`；阈值为正整数；状态可启用/停用。
* **FR-RATELIMIT-02 多规则叠加（P1）**：同一 ApiKey / 客户端可被多个规则覆盖，触发任一即拒绝；规则之间优先级可见但本次不展开算法。
* **FR-RATELIMIT-03 规则生效与变更（P0）**：管理端编辑保存后应能在期望时间内生效（具体时效由实现选择"快速下发/定时拉取"，文档不做强约束）。
* **FR-RATELIMIT-04 限流命中可观测（P0）**：被限流的请求需在 `api_log` 中可被查询（按 ApiKey/客户端维度的命中次数）。
* **FR-RATELIMIT-05 例外（白名单）（P1）**：可对单个 ApiKey 设置"无限流"例外标签。
* **FR-RATELIMIT-06 默认规则（P1）**：可设置"全局默认限流"，用于未匹配任何规则的调用方。

### 4.9 运行中 Sandbox 会话管理（FR-SESSION）

* **FR-SESSION-01 活跃会话列表（P0）**：展示当前所有内存中的会话：含 `sessionId`、所属 `containerId`、`容器名`、`创建时间`、`最后活跃时间`、`归属 ApiKey / 客户端`、`是否默认会话`。
* **FR-SESSION-02 筛选（P1）**：按 ApiKey / 客户端 / 用户 / 活跃度（最近 N 分钟）/ 默认会话过滤。
* **FR-SESSION-03 详情（P1）**：点开看到该会话的最近若干条 `sandbox_operation_log` 与对应 `api_log`。
* **FR-SESSION-04 强制销毁（P0）**：管理员对单个会话发起销毁，前端二次确认，确认后调用 `python-sandbox` 现有"销毁会话"语义；销毁结果回写到界面。
* **FR-SESSION-05 默认会话保护（P1）**：`default` 会话被销毁需二次确认，且只在"管理员显式操作"时执行。
* **FR-SESSION-06 批量清理（P2）**：可选支持对"无活跃度超过 N 分钟"的一批会话执行清理。

### 4.10 调用记录查询（FR-LOG-QUERY）

> 描述的是"管理端查询能力"，不是"日志采集能力"（日志已由 `python-sandbox` 自动落库）。

* **FR-LOG-01 API 日志列表（P0）**：字段见 `api_log`；筛选支持：时间范围、ApiKey、客户端、用户、HTTP 方法、接口路径、响应状态码、traceId、`client_ip`。
* **FR-LOG-02 沙箱操作日志列表（P0）**：字段见 `sandbox_operation_log`；筛选支持：时间范围、操作类型、结果、traceId、`sessionId`。
* **FR-LOG-03 链路详情（P0）**：通过 `traceId` 串联"一次请求 → 多次沙箱操作"；同屏展示原始 `request_params`、执行耗时、`stdout/stderr`、`exit_code`、`error_message`。
* **FR-LOG-04 长内容截断提示（P0）**：当 `request_params / stdout / stderr / operation_content` 被截断时，详情页需明示"内容被截断"。
* **FR-LOG-05 分页与排序（P0）**：基于时间倒序为默认，支持自定义排序与字段排序。
* **FR-LOG-06 导出（P2）**：将筛选后的结果导出为 CSV/Excel。
* **FR-LOG-07 数据隔离（P0）**：普通用户仅可看到自己名下 ApiKey / 客户端 / 用户产生的日志；管理员与审计员看全部（详见 §4.11）。

### 4.11 RBAC 数据可见性（FR-RBAC）

* **FR-RBAC-01 管理员/审计员（P0）**：可见全部数据。
* **FR-RBAC-02 普通用户（P0）**：在客户端/ApiKey/调用记录/运行中会话四个域内，仅可见"归属用户为自己"的记录。
* **FR-RBAC-03 归属判断口径（P0）**：以"客户端的归属用户"与"ApiKey 的绑定用户"二者并集为可见域来源。
* **FR-RBAC-04 越权访问拦截（P0）**：越权时接口返回明确语义，前端按"无权限"页面表达。

### 4.12 操作日志 / 登录日志（FR-AUDIT）

* **FR-AUDIT-01 登录日志（P0）**：写入字段包括用户名、登录时间、登录 IP、UA、结果（成功/失败/被锁）、失败原因；列表支持按用户/时间/IP/结果筛选。
* **FR-AUDIT-02 操作日志（P0）**：管理端每一次"写"操作（新增/编辑/删除/启停/撤销/重置/强制销毁）均留痕；写入字段包括操作人、操作时间、模块名、操作类型、目标对象与主键、变更前后关键字段、客户端 IP、UA、结果。
* **FR-AUDIT-03 查看入口（P0）**：管理员可在"审计日志"菜单查看，审计员只读。
* **FR-AUDIT-04 不可篡改约束（P0）**：审计表只允许新增，业务侧不可修改/删除；删除权限不开放给任何角色。
* **FR-AUDIT-05 操作人上下文（P0）**：操作人 = 当前登录管理端用户；登录前无需"操作人"。

### 4.13 系统设置 / 通知公告（FR-SYS，P2 可选）

* **FR-SYS-01 全局开关（P2）**：维护"是否允许新注册"、"登录失败阈值/锁定时长"、"最长免登天数"、"默认限流值"等可见配置项。
* **FR-SYS-02 通知公告（P2）**：管理员可发布公告，字段含标题、内容、生效时间、失效时间、置顶。
* **FR-SYS-03 公告投递（P2）**：登录后顶部通栏+站内信列表展示未读公告。

## 5. 数据需求

### 5.1 需要新建的实体（与原表同库）

| 实体 | 核心字段（非穷举） | 关键约束 |
|------|--------------------|----------|
| 用户（admin_user） | 用户名、昵称、姓名、邮箱、手机、头像、状态、最后登录时间、密码哈希、盐、登录失败次数、锁定到期时间、是否首次登录、所属部门 | 用户名唯一；状态含启用/停用；含"自身密码修改"必要字段 |
| 角色（admin_role） | 名称、权限字符、排序、状态、备注 | 权限字符唯一；系统内置角色不可删除 |
| 菜单（admin_menu） | 父级、类型、名称、图标、排序、路由、组件、是否外链、是否缓存、是否可见、权限字符（按钮型使用） | 树形结构；权限字符可空 |
| 用户—角色（admin_user_role） | 用户 ID、角色 ID | 联合主键 |
| 角色—菜单（admin_role_menu） | 角色 ID、菜单 ID | 联合主键 |
| 部门（admin_dept，可选） | 父级、名称、负责人、排序、状态 | 树形 |
| 客户端（client_app） | 客户端名称、客户端编码、描述、归属用户、状态、备注 | 编码唯一 |
| ApiKey（client_api_key） | 名称、绑定客户端、绑定用户、密钥前缀、后 4 位掩码、生效时间、过期时间、状态（启用/停用/已撤销/已过期）、备注、明文一次性标记 | 仅一次性明文可被前端"展示一次"；前缀+掩码可重复展示 |
| 限流规则（ratelimit_rule） | 维度类型（ApiKey/客户端）、目标主键、窗口类型（分钟/小时/天）、阈值、状态、生效时间、失效时间 | 一条规则只对应一个目标 |
| 限流命中日志（ratelimit_hit_log，可选新建或共用 api_log） | ApiKey、客户端、规则 ID、命中时间、traceId | 见 §10 开放问题 |
| 登录日志（admin_login_log） | 用户名、登录时间、IP、UA、结果、失败原因 | 只追加 |
| 操作日志（admin_op_log） | 操作人、操作时间、模块、操作类型、对象主键、变更摘要（JSON 字符串）、IP、UA、结果 | 只追加 |
| 公告（sys_notice，可选） | 标题、内容、生效、失效、置顶、发布人 | 见 §4.13 |

> 上表只列字段主线，详细列与索引留给 Design 阶段。

### 5.2 现有表需要扩展的方向（用于 §6 的对接）

* `api_log` 需要新增"客户端 ID / ApiKey ID / 归属用户 ID / 限流命中标志 / 响应耗时分段"。
* `sandbox_operation_log` 需要新增"归属客户端 ID / 归属 ApiKey ID / 归属用户 ID"。
* 上述为"对接要求"，具体列名/类型由 Design 阶段落实。

### 5.3 关键数据流（文字级）

1. **登录流**：用户 → 管理端登录页 → 校验账密 + 验证码 → 颁发管理端会话 → 加载"自身角色 → 可见菜单 → 可访问路由"。
2. **ApiKey 下发流**：管理员/普通用户创建客户端 → 创建 ApiKey → 系统生成明文 → 仅一次性展示 → 落库（仅存哈希或仅存前缀+掩码的语义详见 §10）。
3. **SDK 调用流**：`python-sandbox` 收到请求 → `traceId` 生成 → 拦截器校验 ApiKey → 命中限流规则 → 通过则继续 → 各 Aspect 落 `api_log`、`sandbox_operation_log`（含已扩展字段）。
4. **会话强销流**：管理员在管理端发起 → 调用 `python-sandbox` 的会话销毁语义（已有 `DELETE /api/sandbox/session/{sessionId}`）→ 回执结果写回界面并写操作日志。
5. **审计回流**：管理端任何写操作落入 `admin_op_log`；登录事件落入 `admin_login_log`。

### 5.4 跨库边界

* 所有表**必须建在同一 MySQL 库**，库名沿用 `sandbox`，避免跨库连接。
* 管理端后端只允许读 `api_log`、`sandbox_operation_log` 与（被授权的）`admin_* / client_* / ratelimit_*` 表；禁止绕过授权读其它库。

## 6. 与 `python-sandbox` 后端的对接清单（约束级）

下列条目是"管理端可被设计与实现所依赖的最小承诺"，原后端需要提供或改造：

### 6.1 ApiKey 校验对接

* `python-sandbox` 后端须在所有 `/api/sandbox/*` 入口处校验 ApiKey；非法/缺失需返回明确错误码。
* 该校验入口需要支持"管理端不下发限流规则时也能裸放"（向后兼容见 §10）。
* 校验通过后须把"客户端 / ApiKey / 归属用户"信息写入线程上下文，供 Aspect 与日志使用。

### 6.2 限流对接

* `python-sandbox` 后端须能在请求处理前判定"是否被限流"；命中后拒绝请求并计入命中日志。
* 规则来源：管理端配置。
* 命中信息需参与 `api_log` 的扩展字段。

### 6.3 运行中会话对接

* 须暴露"列出所有活跃会话"接口，字段含 `sessionId`、`containerId`、`容器名`、`创建时间`、`最后活跃时间`、`是否默认`。
* 须暴露"按 sessionId 强制销毁"接口，已有 `DELETE /api/sandbox/session/{sessionId}` 即可沿用。
* 须支持"按 客户端/ApiKey/用户"维度反查其当前活跃 session 集合（接口细节由 Design 落地）。

### 6.4 日志表扩展对接

* `api_log` 与 `sandbox_operation_log` 的扩展字段必须兼容写入；已有写库逻辑（`ApiLogAspect` / `SandboxOperationLogAspect`）不被破坏，新增字段在数据为空时允许为 NULL。

### 6.5 管理端 → `python-sandbox` 内部调用鉴权

* 管理端主动调用 `python-sandbox` 的对接接口时，需在请求中携带"管理端身份"；该身份由管理端单点维护，用于运营审计。
* 该身份不应与"客户端 ApiKey"复用同一鉴权通道。

## 7. 用户故事索引

> 仅列代表性故事，完整集合在 Design 阶段细化。

### 7.1 故事 A：管理员创建一个新客户端并下发 ApiKey

**作为** 系统管理员 **我想要** 为业务团队 A 创建客户端 `teamA-prod` 并生成一把带过期时间的 ApiKey **以便于** 团队 A 的 SDK 接入受限定的能力。

**验收条件**：

* 客户端编码 `teamA-prod` 唯一，否则给出明确错误。
* ApiKey 创建后明文只展示一次（前端一次性提示）。
* 切换到 `python-sandbox` 后立即可用，且超出限流阈值时被拒绝。
* 列表中能按客户端/状态/过期时间筛选并看到该 ApiKey。

### 7.2 故事 B：管理员回收一个失控会话

**作为** 管理员 **我想要** 在运行中会话列表看到一个超时未被回收的容器 **以便于** 强制销毁以释放宿主资源。

**验收条件**：

* 列表展示该 sessionId、container、归属客户端、最后活跃时间。
* 强制销毁有二次确认，默认会话二次强调。
* 销毁后该行从活跃列表消失，调用 `api_log` 也能见到一次"管理员强销"留下的痕迹。

### 7.3 故事 C：业务方按 traceId 排查一次失败

**作为** 普通用户 **我想要** 在日志检索框输入 `traceId` 看到这次请求的所有沙箱操作 **以便于** 我能快速告诉用户是哪一步出错。

**验收条件**：

* 按 traceId 检索到的 API 日志与沙箱操作日志在同一页面呈现。
* 截断字段被明确标注。
* 仅展示本人名下的数据。

### 7.4 故事 D：管理员给一个新同事开通账号

**作为** 管理员 **我想要** 创建账号、绑定"普通用户"角色 **以便于** 新同事能自服务地管理自己名下的客户端。

**验收条件**：

* 新账号首次登录被强制改密。
* 新账号能看见"普通用户"角色的菜单，看不见"用户/角色/审计"等管理菜单。
* 新账号的数据可见性严格为自己名下。

## 8. 与现有约定的一致性

* 数据库：复用 `sandbox` 库，字符集 `utf8mb4`，命名沿用蛇形命名（如 `admin_user`、`client_app` 等）。
* HTTP 响应：管理端对外响应结构与 `python-sandbox` 现有 `Map<String,Object>` 的语义保持"成功 = 业务数据 / 失败 = 统一错误码"两种风格均可，由 Design 阶段选其一并贯穿。
* 接入点：管理端的接口不应直接被 SDK 调用；`/api/sandbox/*` 路径空间保持只属于 `python-sandbox`。
* API 命名：管理端内部使用 `/admin-api/...` 之类的名字以避免与 `/api/sandbox` 冲突。

---

## 9. 验收原则（粗线条）

后续每个 `FR` 验收时按"FR 编号 → 验收要点"逐条勾选。仅描述业务层不变量，不涉及测试手段与覆盖率。

* 任何"写"操作成功 → 列表能即时看到该变更（短时延刷新或被动刷新均可）。
* 任何"鉴权/权限"动作被绕过 → 接口层不能返回业务数据，应被中间层挡下。
* 任何"限流/启停/撤销/过期"语义改变 → 对应 ApiKey 在 `python-sandbox` 端的真实行为可在日志中复盘。
* 任何"创建 ApiKey"动作 → 该 ApiKey 明文只展示一次。
* 普通用户访问越权 → 看不到越权数据，越权记录可被管理员审计。

## 10. 假设、依赖与开放问题

### 10.1 假设（默认采纳，如不认可请在设计前指出）

1. 管理端后端与 `python-sandbox` 后端可以部署在同一台/同一个网络域内的两套服务，使用同一 MySQL；管理端对 `python-sandbox` 的调用通过"管理端身份"鉴别。
2. `python-sandbox` 当前"内存 Map 维护活跃会话"的模型暂不持久化；管理端对此只能"实时看到内存中的会话"，重启期内的"孤儿容器"无法被管理端枚举（残留清理仍走现有定时任务）。
3. 原 `/api/sandbox/*` 的接口契约保持稳定，管理端不调用其任何"破坏语义"的接口。
4. 管理端登录失败的锁定阈值与时长默认采用业界常见值（连续 5 次失败 / 锁定 30 分钟），可在系统设置中调整。

### 10.2 依赖

* 既有 `api_log`、`sandbox_operation_log` 表的存在与字段语义。
* 既有 `TraceFilter` / `ApiLogAspect` / `SandboxOperationLogAspect` 的拦截顺序与上下文传递方式。
* 既有 `SandboxService.removeContainer(...)` 用于销毁会话的语义。

### 10.3 开放问题（建议在进入架构设计前与用户确认）

> 这些问题可能影响模块边界、接口拆分与字段命名，希望逐条给出取舍。

1. **ApiKey 明文存与不存**：是"明文不存库、仅一次性展示"（不可恢复，需要重新生成），还是"明文哈希存库、可在期限内再展示"（更友好但与一次性语义冲突）？**建议前者**，但请用户确认。
2. **限流命中日志是否独立建表**：是在 `api_log` 上扩展"限流命中"标志位，还是单独建 `ratelimit_hit_log`？**建议复用 `api_log` 字段+状态**，请确认。
3. **限流规则下发时效**：管理端保存后是"立即推送"还是"定期拉取"？两种皆可，Design 阶段定。文档不做强约束。
4. **客户端归属用户是否必填**：是否允许"客户端无归属用户"（纯按客户端维度计）？**建议允许为空**，归零的客户端将由管理员统一背书。
5. **审计员是否单独建角色**：是否落地"审计员"这一只读角色？还是由普通"管理员"的"只读视图"承担？**建议单独建**，可降低人为越权风险。
6. **多端登录策略**：同一管理端账号是否允许多端同时在线？强制下线逻辑如何？**建议默认禁止多端**。
7. **会话强销的回执粒度**：界面只展示成功/失败，还是需要"清理容器 / 移除会话 / 取消进行中命令"等细粒度状态？**建议先展示成功/失败**，后续可补。
8. **数据隔离的"含删除"语义**：普通用户被停用/删除后，其历史日志由谁看？**建议停用后管理员仍可见**。
9. **对接接口内部鉴权载体**：管理端调用 `python-sandbox` 的对接接口，应使用何种内部凭证？是否需要随管理端账号绑定？**建议单独维护一组"系统级调用凭证"**。
10. **`python-sandbox` 是否要新增"匿名可访问"白名单**：历史 SDK 调用方是否在迁移期内保留匿名调用能力？**建议提供"灰度开关"，先以"严格"为默认**，迁移完成后再放开。
11. **数据库建表时的初值脚本**：是否需要一份"管理端"侧的初始化 SQL（DML）作为种子数据（如内置菜单、内置角色、超级管理员账号）？**建议提供**。
12. **审计日志的呈现口径**：是否需要在"操作对象"上记录"对象主键 + 对象名/编码"以便人工快速定位？**建议记录**。
